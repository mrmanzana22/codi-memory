## Layer 3: Sleep Loop Tick Metrics

**Important:** Based on 1 manual run only. Not statistically significant. Launchd job created to collect production data.

| Tick | SLO p95 | Real (1 run) | Verdict |
|------|---------|--------------|---------|
| prospective | 1,000ms | 3ms | PASS |
| health | 2,000ms | 6,085ms | **FAIL (3x over)** |
| consolidation | 4,000ms | 1,249ms | PASS |
| homeostasis | 3,000ms | 127ms | PASS |
| **Total** | 8,000ms | **7,480ms** | PASS (93.5% of budget) |

### Health Tick Root Cause

The health tick calls `_verificar_salud_memoria_interna()` which:
1. Connects to Qdrant Cloud (first connection = TLS handshake + auth)
2. Initializes mem0 client (creates indices if needed)
3. Counts memories and checks collections

On cold start, steps 1-2 dominate at ~4-5s. After warm-up, health check should be <500ms.

**Mitigation (PR #2):** Add explicit warmup at start of `run_sleep_loop()` — a lightweight Qdrant ping that forces connection init before ticks begin. This avoids changing TICK_ORDER while eliminating cold-start penalty from tick measurements.

### Missing: Launchd Job

**Finding:** No launchd job existed for the sleep loop. The existing `com.codi.consolidation` job runs `scripts/run_consolidation.py` (autonomous consolidation), not the sleep loop.

**Fix:** Created `deploy/com.codi.sleep_loop.plist` — runs every 30 min via `python -m modules.sleep_loop --reason launchd`.

## Operational Reference

### Installing the sleep loop job

```bash
# Copy plist to LaunchAgents
cp deploy/com.codi.sleep_loop.plist ~/Library/LaunchAgents/

# Load (starts the 30-min schedule)
launchctl load ~/Library/LaunchAgents/com.codi.sleep_loop.plist

# Verify loaded
launchctl list | grep sleep_loop

# Unload (stops schedule)
launchctl unload ~/Library/LaunchAgents/com.codi.sleep_loop.plist
```
